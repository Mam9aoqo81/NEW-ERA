# حدود الطلبات والحصص — 0.12

هذه حدود تطبيق أولية وليست اعتمادًا للإطلاق العام أو بديلًا لـreverse proxy/WAF وحدود حجم الطلب والاتصالات والتكلفة.

## الحدود الافتراضية

كل ميزانية زمنية نافذة ثابتة من 60 ثانية حسب ساعة الخادم. عند حد النافذة يمكن حدوث دفعتين متتاليتين؛ ليست sliding window أو نظام مكافحة هجوم موزع.

| الإعداد (بادئة `KNOWLM_`) | الافتراضي | النطاق |
|---|---:|---|
| `AUTH_PER_MINUTE` | 60 | تسجيل الحساب والدخول معًا، لكل عنوان عميل يراه ASGI |
| `MUTATIONS_PER_MINUTE` | 120 | كل POST/PUT/PATCH/DELETE تحت `/v1/`، للمستخدم الموثّق أو عنوان العميل عند غياب جلسة صالحة |
| `ASK_PER_MINUTE` | 30 | الأسئلة، لكل مستخدم عبر جميع دفاتره وجلساته |
| `INGESTION_PER_MINUTE` | 10 | النص وPDF المتزامن ومهام PDF وDOCX وYouTube، لكل مستخدم |
| `ACCOUNT_DELETE_PER_MINUTE` | 5 | طلبات حذف الحساب، لكل مستخدم، بما فيها كلمة مرور خاطئة |
| `MAX_NOTEBOOKS` | 20 | دفاتر كل مستخدم |
| `MAX_SOURCES_PER_NOTEBOOK` | 100 | مصادر كل دفتر، بما فيها المعالجة والفاشلة |
| `MAX_ACTIVE_JOBS_PER_NOTEBOOK` | 4 | المصادر في حالة processing، وتشمل المهام المنتظرة والجارية |

الحد العام يعمل إضافة للحد المتخصص، وليس بديلًا عنه. الطلبات غير الصالحة ومحاولات الإعادة تُحسب أيضًا. طلبات GET والقراءة وhealth لا تُحسب، لكن تسجيل الخروج POST يُحسب ضمن الحد العام. حد التسجيل والدخول لا يُتجاوز بإرسال Bearer مزيف. الجلسات المتعددة للمستخدم تشترك في ميزانياته. كل القيم أعداد صحيحة من 1 إلى مليون؛ إعداد غير صالح يرفض بدء التطبيق، ولا يوجد تعطيل خفي بالقيمة صفر.

429 يعيد `Retry-After` بالثواني و`Cache-Control: no-store`؛ تعرض الواجهة وقت الانتظار ولا تنهي الجلسة. لا تعيد الواجهة الطلب تلقائيًا لتجنب تكرار تكلفة مزوّد خارجي. تعطل مخزن الميزانيات ينتج 503 ولا يفتح الطلبات بلا حدود. 409 للحصص البنيوية لا يعني انتظار دقيقة: احذف دفترًا لم تعد تحتاجه أو استخدم دفترًا آخر للمصادر أو انتظر انتهاء مهمة لمعالجة سقف المهام. لا يوجد حذف مصدر منفرد حاليًا. إتمام المهمة أو فشلها يحرر خانة المعالجة، لكنه لا يحرر خانة المصدر. إعادة محاولة مهمة فاشلة تحترم سقف المعالجة ولا تستهلك خانة مصدر جديدة.

## التخزين والتزامن والخصوصية

جدول `rate_buckets` يحفظ عدادات ذرية بـUPSERT، ومفتاحًا مشتقًا بـSHA-256 من النطاق والهوية والنافذة، ومعرّف مستخدم للجلسات الصالحة، ووقت انتهاء. لا يحفظ كلمات مرور أو رموز جلسات أو أسئلة أو نصوص المصادر. تجزئة IP ليست إخفاء هوية مضمونًا؛ يجب اعتبارها بيانات مستعارة ذات اعتبارات خصوصية.

العدادات مشتركة بين نسخ التطبيق التي تستخدم قاعدة البيانات نفسها، وتستمر بعد إعادة التشغيل. تُنظف النوافذ المنتهية عند أول طلب كتابة لاحق؛ لا توجد مهمة مجدولة تمحوها عند خمول الخدمة. حذف الحساب يمحو صفوف الميزانية المرتبطة بمعرّفه، لا كل صفوف IP المجهولة المستخدمة قبل دخوله. التسجيل والدخول يستخدمان IP حتى عند إرفاق جلسة.

تستخدم الحصص قفل كتابة على الأصل ثم العد والإدراج في transaction واحدة. الاختبارات المتزامنة على SQLite تثبت عدم زيادة العدد عن الحصة؛ بعض حالات التنافس قد ترجع 503 بدل إتمام الطلب. PostgreSQL يستخدم مسار UPSERT وقفلًا مماثلًا لكن لم يُختبر فعليًا هنا. الحصص الجديدة لا تحذف بيانات موجودة تتجاوز الحدود: تمنع الإضافات فقط. عدّل الحدود بعناية وأعد تشغيل كل نسخ API بالإعداد نفسه.

## إعداد البروكسي

في المعاينة نشغّل Uvicorn باستخدام `--no-proxy-headers` حتى لا يغيّر عميل غير موثوق عنوانه عبر `X-Forwarded-For`. نتيجة ذلك أن Vite/البروكسي المحلي قد يجعل جميع الزوار يتشاركون عنوانًا واحدًا لميزانية المصادقة. حدود المستخدم بعد الدخول لا تتأثر بتشارك العنوان.

للإنتاج: اضبط بوابة موثوقة تزيل headers الواردة وتعيد بناء عنوان العميل، واقصر الوصول المباشر للخادم عليها، واضبط قائمة الثقة في Uvicorn لعناوينها الدقيقة. لا تستخدم الثقة بـ`*` عشوائيًا. middleware لا يقرأ `X-Forwarded-For` بنفسه، لكنه يتلقى عنوان ASGI الذي قد يكون الخادم أعاد كتابته؛ الإعداد الخاطئ في Uvicorn يظل خطرًا. يلزم تحديد معدل عند البوابة أيضًا، لا الاعتماد على عمليات كتابة DB لمقاومة DDoS.

## التشغيل والقبول المتبقي

نفّذ `alembic upgrade head` لتطبيق `14456e92e1cc` قبل إعادة تشغيل API؛ عدم وجود الجدول يجعل طلبات الكتابة تفشل مغلقة بـ503. ترجيع الترحيل يحذف العدادات، لا مصادر الدراسة. `.env.example` يوثّق القيم؛ ملفات env لا تُحمّل تلقائيًا بواسطة Python.

الاختبارات تغطي استمرار العدادات، اشتراك الجلسات، اختلاف المستخدمين، محاولات تزوير headers، إعادة النافذة، الزيادة الذرية المتزامنة، حصص كل مسارات الاستيراد وإعادة المحاولة وتحرير السعة، وحذف عدادات المستخدم. اختبارات الواجهة تغطي الرسائل وRetry-After. اختبار المتصفح الجديد يستنفد حد الأسئلة عبر API الحقيقي ثم يعيد تشغيل **نفس استجابة الرفض** لطلب الواجهة لتجنب تغير الدقيقة أثناء تحميل الصفحة؛ ليس كل طلب في هذا الاختبار غير محاكى. اختبارات التدفقات العشرة السابقة تستمر دون هذا الاعتراض.

ما يزال مطلوبًا: حماية المصادقة حسب الحساب ضد هجوم موزع، حدود قراءة وحجم طلب عند البوابة، حصص bytes وتكلفة LLM يومية، حصص للمحادثات والبطاقات والنتائج، حد تزامن عالمي للمعالجة، اختبار حمل وPostgreSQL، ومراقبة وتنبيهات. هذه الدفعة لا تستوفي بقية ميزات المجتمع أو التعاون أو الصوت أو RAG الدلالي.
